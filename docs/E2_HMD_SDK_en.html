Overview: Two Libraries & Loading

The SDK is split into two dlopen-able shared libraries, each exporting a single symbol that fills a versioned vtable. Applications normally include only sxr_recorder.h; the HAL is loaded internally by the recorder and is generally invisible to the app.

Loading paths

  • recorder: the inline loader in sxr_recorder.h tries /customer/sd/libsxr_recorder.so first, then /customer/sample_code/lib/. Returns NULL if not found.
  • HAL: hal_loader.cpp tries the bare name libsxr_hal.so first (requires LD_LIBRARY_PATH), then /customer/sd/ and /customer/sample_code/lib/. The HAL is integrated in the ROM — developers never need to touch or push it; the loader's fallback paths hit it automatically.
ℹ️

The HAL must be loaded with RTLD_GLOBAL. libsxr_hal.so pulls in the underlying libmi_*.so, which are in global scope when the app links them directly; if dlopen'ed with RTLD_LOCAL, symbol resolution between MI libraries fails ("can't resolve symbol"). The recorder side is MI-free and carries no symbol-conflict risk.

The HAL embeds RPATH /config/lib, so its MI dependencies (located under /config/lib) self-locate. On the app side, LD_LIBRARY_PATH=/customer/sd (the directory holding the recorder) is all that's needed.

Minimal Workflow

Recommended usage: use libsxr_recorder only, with all parameters at their library defaults. The entire recording session is a singleton:

①
record_init
Build pipeline (default config)
start IMU/mag threads
optionally start preview callback
→
②
record_start(dir)
Start a segment asynchronously
force IDR → STARTED
→
③
Recording…
Writes Camera{0,1}/
Sensors/ + Audio/
→
④
record_stop
Close video.mp4
(write back moov), finalize segment
→
⑤
record_deinit
Finalize any lingering segment
stop threads, tear down pipeline

Steps ②–④ can loop over N segments (each with its own clip_NNN/ directory) without restarting the pipeline; you can also call record_rotate(new_dir) during recording to atomically switch to a new directory (no stop, no dropped frames, no cross-file mixing).

⚠️

record_start is asynchronous. A return of 0 only means it was enqueued; actual disk writing begins only after the SXR_REC_EVT_STARTED event (dispatched once both eyes have captured the forced IDR). Calling record_stop immediately without waiting yields empty files. IDR_TIMEOUT / WRITE_ERROR events auto-finalize the segment.

API Reference

libsxr_recorder — 6 APIs (v3 vtable)

FunctionPurposeReturns
record_init(preview_cb, userdata) Singleton init: builds the stereo pipeline internally + starts IMU/mag threads; if preview_cb is given, also starts sub-stream frame grab. Can be init'ed/deinit'ed repeatedly 0 success; −1 failure (not initialized)
record_deinit() Teardown: finalizes any still-active record segment → stops preview dispatch/sensor threads → tears down the pipeline. Idempotent —

Event callback sxr_rec_event_cb_t

typedef enum {
    SXR_REC_EVT_STARTED,       // both eyes' first IDR written; recording in progress
    SXR_REC_EVT_IDR_TIMEOUT,   // forced-IDR timeout (default 1s) → auto-finalize, no data
    SXR_REC_EVT_WRITE_ERROR,   // write failure → auto-finalize, files may be incomplete
} sxr_rec_evt_t;
typedef void (*sxr_rec_event_cb_t)(sxr_rec_evt_t evt, int error_code, void *userdata);
⚠️

Event callbacks run on a library-internal thread. They must be short and non-blocking; never call record_* from inside a callback (set a flag and handle it in your main loop). An error event only withdraws the segment and marks it STOPPING; record_stop is idempotent on an already-STOPPING segment, and finalization is still driven by the app's call.

Preview callback sxr_frame_cb_t (optional)

typedef void (*sxr_frame_cb_t)(int pipe_id, int ch,
    const uint8_t *data, size_t size, int64_t pts_us, int is_sync,
    const uint8_t *csd, size_t csd_size, void *userdata);
  • Receives sub-stream encoded frames: ch=1 (Cam0), ch=3 (Cam1). Runs for the whole preview period, zero disk writes.
  • The callback executes on a library-internal dispatch thread (the HAL grab thread only enqueues), but it is still an internal thread — return quickly; when the queue is full the oldest frame is dropped to keep the newest.
  • If preview_cb is not provided, sub-stream frame grab is not started at all.

Data type sxr_imu_sample_t

typedef struct {
    double  accel[3];   // m/s², body frame
    double  gyro[3];    // rad/s, body frame
    double  mag[3];     // μT
    int64_t ts_ns;      // CLOCK_MONOTONIC_RAW (runtime cache domain; converted to *_utc_ns via the UTC bridge when written to dataset CSVs)
} sxr_imu_sample_t;

Output: the dataset

Each record_start(dir) produces a complete dataset under dir (video/metadata/sensors/audio/calibration); see Part II for the structure and fields.

✓

Usage notes: always write output to the SD card (/customer/sd/); /tmp is tmpfs and writing large files there will OOM the device. The same app can run init/start/stop/deinit repeatedly; switching across apps (e.g. to the reference demo prog_pipeline) requires adb reboot.

Custom Configuration: Using libsxr_hal Directly

libsxr_recorder runs on fixed defaults. To change bitrate / GOP / preview / audio / clocks etc., bypass the recorder and call libsxr_hal directly: pipeline_create_venc(SxrPipelineConfig*) builds the pipeline → build your own frame grab/sensors, and write to disk yourself. The sxr_hal_api_t vtable loaded by the recorder is as follows.

ℹ️

The structs have been simplified. SxrPipelineConfig no longer exposes camera_case / pad / device / iq_path / output_dir: sensor detection, main-stream resolution, and the IQ bin are all decided automatically by the HAL from the sensor models mounted on pad0/pad2 (SC235HGS=1600×1200, SC233HGS=1920×1200), with results filled back into camera_mask / width[] / height[] / pts_offset_ns.

typedef struct SxrPipelineConfig {
    /* Input (configurable; 0 = use default) */
    int   isp_clk;             // ISP clock Hz, default 216M
    int   scl_clk;             // SCL clock Hz, default 288M
    int   venc_gop;             // default 30 (IP-only, no B-frames)
    int   venc_bitrate_bps;     // unit bps, default 4 Mbps
    int   enable_preview;       // 0=off 1=sub-stream on
    int   preview_width;        // 0=auto -> main/4 (filled back by sensor model)
    int   preview_height;       // 0=auto -> main/4
    int   preview_bitrate_bps;  // 0=auto -> 2 Mbps
    int   preview_fps;          // 0=auto -> 15
    volatile unsigned char *exit_flag;  // exit signal
    SxrAudioConfig audio;     // audio (16k/2ch/S16LE default)

    /* [Output] filled back by pipeline_create_venc: auto-detects the sensors
     * mounted on pad0/pad2 and decides main-stream resolution and IQ bin by model */
    int   camera_mask;          // bit0=Camera0, bit1=Camera1; 0=no sensor
    int   width[SXR_RECORDER_SNR_MAX];   // per-camera main-stream width (detected)

There are also SxrRecordConfig (prealloc_bytes / sample_interval_us), SxrRecordStats (frame/byte/drop statistics), and SxrAudioConfig (gain/sample rate). The recorder embeds all defaults; you only face these types directly when customizing.

Complete Usage Example

Reference caller fmp4_recorder/main.cpp (build artifact prog_fmp4_recorder, standalone test tool): previews for the whole session, records N segments in a loop, then reads the IMU — using only the public libsxr_recorder API. The system default prog_sxrservice (sdk/verify/sample_code/demo/sxrservice) drives the recorder the same way through recorder_bridge.c, plus business logic such as BLE/WiFi/WS preview on top.

#include "sxr_recorder.h"

static volatile unsigned char g_bExit = 0;
static volatile unsigned char g_recStarted = 0;
static void sig_handler(int sig){ (void)sig; g_bExit = 1; }

/* Preview callback: sub-stream ch1/ch3 encoded frames; runs on a library thread, return quickly */
static void preview_cb(int pipe_id, int ch, const uint8_t *data, size_t size,
                         int64_t pts_us, int is_sync,
                         const uint8_t *csd, size_t csd_size, void *ud)
{ /* forward to WS / display etc. */ (void)pipe_id;(void)ch;(void)data;(void)size;(void)is_sync;(void)csd;(void)csd_size;(void)ud; }

/* Record-segment event callback: only set flags, never call record_* here */
static void evt_cb(sxr_rec_evt_t evt, int err, void *ud) {
    (void)ud;
    if (evt == SXR_REC_EVT_STARTED) g_recStarted = 1;
    else { printf("record event err=%d\n", err); g_bExit = 1; }
}

int main(int argc, char **argv) {
    signal(SIGINT, sig_handler); signal(SIGTERM, sig_handler);

    /* ① Load libsxr_recorder.so (dlopen + vtable; NULL if not found) */
    const sxr_recorder_api_t *REC = sxr_recorder_api();
    if (!REC) { fprintf(stderr, "load libsxr_recorder.so failed\n"); return -1; }

    /* ② Init (default stereo + IMU + audio; resolution auto-detected by sensor; preview on if preview_cb given) */
    if (REC->record_init(preview_cb, NULL) != 0) { fprintf(stderr, "record_init failed\n"); return -1; }
    sleep(2);   // wait for AE/AWB convergence, pipeline ready

    /* ③ Record N segments, each with its own clip_NNN/ directory */
    for (int seg = 1; seg <= segs && !g_bExit; seg++) {
        char dir[640];
        snprintf(dir, sizeof dir, "/customer/sd/fmp4_recorder/clip_%03d", seg);
        g_recStarted = 0;
        if (REC->record_start(dir, evt_cb, NULL) != 0) break;  // async
        while (!g_recStarted && !g_bExit) usleep(20000);        // wait for STARTED
        sleep(segdur);                                    // record
        REC->record_stop();                                     // finalize this segment (moov write-back)
    }

    /* ④ Read latest IMU values (optional, O(1)) */
    sxr_imu_sample_t s;
    if (REC->imu_get_latest(&s) == 0)
        printf("a=(%.2f,%.2f,%.2f) g=(%.2f,%.2f,%.2f) m=(%.1f,%.1f,%.1f) ts=%lld\n",
               s.accel[0], s.accel[1], s.accel[2],
               s.gyro[0], s.gyro[1], s.gyro[2],
               s.mag[0], s.mag[1], s.mag[2], (long long)s.ts_ns);

    /* ⑤ Teardown (idempotent; finalizes even if record_stop was skipped) */
    REC->record_deinit();
    return 0;
}
✓

Part II · Dataset Structure & Formats

Recorded Dataset

File structure and field semantics of the recording output (clip_NNN/) — video / sensors / audio / calibration / alignment & conversion.

Overview

ℹ️

Key fact: the on-disk physical timestamps (video exposure exposure_start_utc_ns, IMU ts_utc_ns, audio ts_utc_ns) are uniformly CLOCK_REALTIME nanoseconds — i.e. Unix-epoch wall-clock time, directly alignable with wall-clock data from other devices. Only the pts_us columns stay on CLOCK_MONOTONIC_RAW (µs), as the join key to the mp4 sample timeline. For converting between the two domains see Time Alignment & Conversion.

Directory Structure

One clip_NNN/ per segment (NNN starts at 001, zero-padded to three digits). Stereo is Camera0 (left eye) + Camera1 (right eye).

<output>/                         # default /customer/sd/fmp4_recorder
└── clip_001/                      # artifacts of one recording segment
    ├── id.txt                     # hardware UUID (plain text)
    ├── Camera0/                     # left eye
    │   ├── video.mp4                # HEVC fMP4
    │   ├── metainfo.csv             # per-frame exposure metadata
    │   └── camera_params.json       # intrinsics + extrinsics
    ├── Camera1/                     # right eye (same layout as Camera0)
    │   ├── video.mp4
    │   ├── metainfo.csv
    │   └── camera_params.json
    ├── Sensors/
    │   ├── accel.csv              # accelerometer
    │   ├── gyro.csv               # gyroscope
    │   ├── mag.csv                # magnetometer
    │   └── imu_calibration.json  # IMU calibration
    └── Audio/                      # optional: the whole directory is absent if there is no microphone
        ├── audio.mp4              # PCM fMP4
        └── metainfo.csv
ℹ️

Each clip_NNN/ is one complete, independent recording segment; the files within it are self-consistent and segments do not affect each other.

Time Bases

On-disk physical timestamps are uniformly CLOCK_REALTIME nanoseconds (Unix-epoch wall clock); the capture chain internally stays on CLOCK_MONOTONIC_RAW (immune to NTP adjustments) and is converted once via the in-library UTC bridge only when files are written. Division of labor between the two domains:

TimestampClock domainMeaning
exposure_start_utc_ns (Camera metainfo)CLOCK_REALTIMEphysical exposure start of that frame (wall clock, convertible to a date directly)
ts_utc_ns (accel/gyro/mag)CLOCK_REALTIMEper-sample timestamp
ts_utc_ns (Audio metainfo)CLOCK_REALTIMEcapture time of that PCM period
pts_us (video/audio metainfo)PTS µs · MONOTONIC_RAW valuejoin key to the mp4 sample timeline (same source as tfdt), used for row↔sample pairing; not wall clock
ℹ️

UTC bridge precision: the offset is seeded at the start of each record segment; afterwards, any conversion thread that finds the cached offset stale (>200 ms) re-samples it inline — no dedicated sampling thread, no sidecar file. With NTP slew ≤500 ppm the worst-case error is ≤0.1 ms; if an NTP step happens mid-recording, timestamps on either side of the step are each locally correct.

Note: on a bare device (no RTC/NTP), CLOCK_REALTIME counts from power-on and tracks MONOTONIC_RAW — there, *_utc_ns values that look like seconds-since-boot are normal; after time sync, recordings return to true epoch time.

⚠️

Do not run date -d on pts_us — that is a monotonic-clock value (magnitude ~1e11–1e12 when expressed in ns), not epoch seconds; it exists only for pairing with mp4 sample PTSs. The *_utc_ns columns are the wall clock.

Video & Metadata (Camera{0,1})

video.mp4 — HEVC fMP4

Fragmented MP4 (ISO BMFF).

  • Container structure: ftyp + moov (up front; finalized at recording end with the actual frame count/duration) + one styp + moof + mdat fragment per GOP.
  • Codec: HEVC Main profile, IP-only (no B-frames), guaranteeing monotonic PTS. The first IDR's VPS/SPS/PPS are assembled into hvcC written into moov.
  • Fragment boundaries: on I-frame boundaries, one fragment per GOP.

metainfo.csv — per-frame exposure metadata

One row per encoded frame.

About the extrinsics

extrinsics describes the camera pose relative to the reference origin — the Tbc (camera → body) in the SVR coordinate frame: position is the translation, rotation the orientation unit quaternion ([x,y,z,w]). Downstream can use it directly as the camera pose.

Distortion model in detail (radialDistortion)

This field describes the lens's geometric distortion. Device calibration declares the model as FISHEYE_4_PARAMETERS — a 4-parameter fisheye radial distortion model. Of the 8-element array, only the first 4 entries are valid; the rest are 0 (no tangential distortion terms).

IndexSourceMeaning
[0..3] = k1, k2, k3, k44 coefficients from calibrationfisheye distortion coefficients (only these 4 are valid)
[4..5]Reserved slotsalways 0, unused
[6..7]Paddingalways 0, filler to reach 8 elements, unused

Basic model: ideal pinhole projection gives normalized image coordinates (x, y); the radius from the principal point is r = √(x² + y²), corresponding to an incidence angle θ = atan(r) between the incoming ray and the optical axis. Fisheye lenses bend wide-angle rays strongly, so coefficients correct the mapping of θ (radius). The 4-parameter fisheye model typically takes the Kannala-Brandt form:

θ_d = θ · (1 + k1·θ² + k2·θ⁴ + k3·θ⁶ + k4·θ⁸)

# θ   = atan(r)          incidence angle for the normalized radius (under pinhole/equidistant projection)
# θ_d                    distorted equivalent angle → projected onto the image plane gives the actual pixel position
# k1..k4                  the 4 distortion coefficients (radialDistortion[0..3])

Parameter meanings:

  • k1: the dominant term; sets the overall direction and magnitude of the radial bending; |k1| is usually far larger than the higher-order terms.
  • k2, k3, k4: higher-order correction terms, mainly affecting large angles (image periphery).
  • The smaller the coefficients, the closer to an ideal pinhole/equidistant projection; on this device they are on the order of 1e-3 ~ 1e-2.
ℹ️

The distortion coefficients are factory calibration values and are passed through as-is in this dataset — no undistortion is applied. Downstream must apply k1..k4 per the FISHEYE_4_PARAMETERS model; the formula above is the typical (Kannala-Brandt) form of a 4-parameter fisheye model — for the vendor's exact polynomial convention, defer to their calibration specification.

Using nonorthogonality

First, be clear: are the CSV values already corrected? The dataset's accel.csv / gyro.csv have only gone through FSR range scaling + the mounting-orientation matrix (chip frame → body frame); the bias / scale_factor / nonorthogonality from imu_calibration.json are not applied. Those three are factory precision-calibration parameters, left for downstream to apply as needed.

What nonorthogonality corrects: the IMU's three axes are not exactly orthogonal due to manufacturing tolerances (angles ≠ 90°), causing inter-axis crosstalk — true acceleration/angular rate on one axis leaks a little into the other two. These parameters exist to remove that coupling; the closer to 0, the better the orthogonality.

How to use: after reading the CSV values, correct in the order bias → scale → nonorth; the final step uses the 3×3 matrix built from the nonorthogonality terms to decouple the axes:

v_true ≈ N⁻¹ · ( (v_csv − bias) ⊘ scale )      # ⊘ element-wise division

# Typical 3-parameter → 3×3 non-orthogonal coupling matrix (lower-triangular, small-angle approximation):
N = ⎡ 1       0       0    ⎤
    ⎢ n_yx    1       0    ⎥
    ⎣ n_zx    n_zy    1    ⎦
# n_yx: the y axis's skew angle relative to the x axis, and so on. A skew (antisymmetric) form may also be used.
  • Order: remove the bias first, then calibrate sensitivity (scale), and finally decouple the axes (nonorth).
  • accel / gyro each have their own set: nonorthogonality.accelerometer and .gyroscope are independent of each other and apply to their respective streams.
  • Magnitude & trade-offs: of the three corrections, bias usually matters most, scale next, nonorth least. General attitude/logging applications can ignore nonorth; high-precision VIO / SLAM should apply it.
⚠️

This dataset passes factory calibration values through as-is, with none of the above corrections applied. The exact form of the 3-parameters-to-3×3 matrix (lower-triangular / skew, whether to multiply N or N⁻¹, whether scale is a multiplier or a divisor) follows the device calibration specification (tracking group); confirm the convention with the vendor before use.

UTC & Timestamp Domains

The device internally (the capture chain) runs on CLOCK_MONOTONIC_RAW — monotonic and NTP-immune; the on-disk physical timestamps are converted to CLOCK_REALTIME at the moment of writing via the in-library UTC bridge, so what you see in the dataset is wall-clock time. How the bridge works:

  • Seeding: at the start of each record segment, a triple bracketed clock read (mono₁ → realtime → mono₂, midpoint taken) yields offset = utc − mono.
  • Self-refresh: all conversions happen on normal-priority writer threads; whenever a thread finds the cached offset stale (>200 ms) it re-samples under the mutex. No dedicated sampling thread.
  • Error bound: NTP slew ≤500 ppm × 200 ms staleness ⇒ worst case ≤0.1 ms; an NTP step falling between two conversions leaves the timestamps on each side locally correct.
ℹ️

Older versions carried this mapping in the sidecar file sensor_time_to_utc.csv (1 Hz samples); it has been removed — the dataset's own per-frame pts_us ↔ exposure_start_utc_ns pairs are the densest mapping samples, and the monotonic domain can be reconstructed from them on demand (see Time Alignment & Conversion).

Time Alignment & Conversion

1. Cross-stream alignment (same domain, direct subtraction)

Video exposure_start_utc_ns, IMU/mag ts_utc_ns, and audio ts_utc_ns are all CLOCK_REALTIME nanoseconds — subtract them directly to get time deltas, no mapping file needed; for stereo pairing, use nearest-neighbor matching of the two streams' exposure_start_utc_ns (first frames are already aligned to the same physical exposure).

2. Video ↔ metainfo pairing

An mp4 sample's PTS (µs) = that metainfo row's pts_us (row order = frame order). To get the frame's wall-clock time, read exposure_start_utc_ns from the same row.

3. MONOTONIC_RAW values ↔ UTC

pts_us and the runtime cache (sxr_imu_sample_t.ts_ns) stay in the monotonic domain. To convert monotonic values to UTC, the dataset itself carries one pair of samples per frame:

(mono_ns, utc_ns) = (pts_us × 1000 − exposure_duration_ns, exposure_start_utc_ns)

Piecewise-linear interpolation over this pair sequence rebuilds a mono→utc mapping of arbitrary precision (tools/dataset_align_check.py does exactly this); equivalently, utc(mono) ≈ mono + offset, where the offset drifts between adjacent frames only from NTP slew.
